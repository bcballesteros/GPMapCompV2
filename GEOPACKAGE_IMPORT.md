# Vector GeoPackage import: implementation and QA handoff

Verified locally on 21 October 2026, on `feat/geopackage-vector-import`.
No branch was created or switched; no commit, push, merge, backend or database
schema change was made.

## Result

Vector `.gpkg` files can be imported through **Add Geospatial Data**. Users select
one or more feature tables and use the existing **Upload** action. Each selected
table becomes an ordinary managed vector layer. Unknown/unreliable CRS and bad
selected feature data fail explicitly before the map is changed. Existing
Shapefile ZIP, GeoJSON, KML and CSV imports were exercised in development and in
the built application.

The reader deliberately excludes raster/tile rendering, GeoPackage editing and
GeoPackage export. Existing map composition, output dimensions, legend placement,
SLD capabilities and Share email behavior were retained.

## Library evaluation and runtime

The selected primary library is **`@ngageoint/geopackage` 4.2.10**, the npm `latest`
stable release at evaluation time. The `beta` tag was 5.0.2-beta and was not used.
The package is MIT licensed. npm release metadata showed the stable release was
published on 7 October 2026; the project has current maintenance activity.
Sources: [official repository](https://github.com/ngageoint/geopackage-js),
[official npm package](https://www.npmjs.com/package/@ngageoint/geopackage).

The installed release was inspected directly, including `package.json`,
`dist/index.js`, `dist/lib/db/sqljsAdapter.js`, `dist/lib/geoPackage.js`,
`dist/lib/features/user/featureDao.js` and `dist/lib/geom/geometryData.js`.
Its browser entry is `dist/geopackage.min.js`; its SQLite dependency is
`rtree-sql.js` 1.7.0. Optional Node/CLI dependencies include `better-sqlite3`,
`inquirer` and `chalk`. Those are not needed or bundled for this browser feature.
Local installation used `npm install --ignore-scripts` to avoid native setup.
The normal npm lockfile update was generated by npm.

The high-level discovery/iteration APIs (`getFeatureTables`, `getFeatureDao`,
`queryForGeoJSONFeaturesInTable`) were reviewed. The application instead uses the
public `SqljsAdapter` and `GeometryData` exports with a focused metadata reader.
This permits explicit identifier quoting, statement cleanup on early failure,
BigInt-safe attribute access, and rejection of unreadable rows instead of a
library iterator silently omitting them. No alternative GeoPackage library or
separate rendering system was introduced.

Explicit coordinate normalization uses the direct **proj4 2.22.0** dependency;
the NGA bundle also contains its own older proj4. The application does not use
the NGA bundle's implicit projection conversion.

Vite imports the upstream browser bundle and its **matching** `sql-wasm.wasm`
as `?url` assets. A module worker dynamically imports that UMD browser bundle,
then calls `setSqljsWasmLocateFile` with the emitted local WASM URL. No engine
code, CanvasKit assets, native SQLite addon or external CDN is required at app
startup. Build output includes the upstream notices and MIT licenses.

## Architecture and files

The original upload architecture was reviewed before integration:

1. Upload handlers retain a selected File and format in the shared store.
2. `parseUploadFile()` reads existing formats into WGS84 GeoJSON and OpenLayers
   features; `shpjs` already normalizes Shapefile coordinates, KML performs its
   own read/write projection conversion, and CSV uses longitude/latitude.
3. `addVectorLayer()` creates shared source, geometry classification, styles,
   labels and layer records. `addLayerItem()` binds the common Layers panel.
4. Export/Share capture those managed layers and their effective legend
   descriptors, without branching on upload format.

The new path keeps those boundaries:

```text
File selection -> lazy session -> worker -> SQLite metadata inspection
    -> checklist -> selected table extraction and CRS normalization
    -> prepared GeoJSON -> existing OpenLayers conversion
    -> addVectorLayer/addLayerItem -> existing styles, legends, Export/Share
```

## Discovery and selection

The reader checks the SQLite signature and GeoPackage application identifier,
runs SQLite `quick_check`, and verifies physical core metadata tables and their
required columns. Only `gpkg_contents.data_type = 'features'` entries are considered
for import. Each must have a matching geometry-column record, a readable physical
feature table, one INTEGER primary key, a supported geometry declaration, usable
CRS, and a positive bounded feature count.

The checklist displays table name, declared geometry type, exact feature count,
CRS identifier and human-readable CRS name. All importable tables start selected,
including the single-table case. Native labeled checkboxes support keyboard use.
Unsupported and empty tables are not selectable; reasons remain in the feedback
area. Raster/tile table counts are reported and those tables are ignored. A
raster-only file reports that this release supports vector data only.

Upload is disabled during discovery and import. Clear, replacement selection,
format changes and modal closure release the selection's worker/database. Read
failures require selecting the file again. Selecting no tables gives feedback
without consuming the open session, so the selection can be corrected and retried.

## CRS and geometry policy

The transformation is:

```text
Original table CRS -> proj4 actual transformation -> EPSG:4326 GeoJSON
    -> existing geojsonToOpenLayers() -> EPSG:3857 map geometry
```

Supported directly: EPSG:4326, EPSG:3857 and WGS84 UTM zones EPSG:32601–32660 and
32701–32760. WGS84 UTM zones 50N and 51N are relevant to Philippine datasets.
Other file WKT/PROJ definitions are considered only when they identify WGS84 or
provide explicit `TOWGS84`/`+towgs84` parameters and proj4 can parse them.
The WKT extension's `definition_12_063` is preferred when present and defined.

PRS92 is not assumed equivalent to WGS84. Missing datum transformation parameters,
unknown identifiers without a reliable definition, required grid files and
unsupported BOUNDCRS definitions are rejected with guidance to reproject to
EPSG:4326 in a GIS. No projection or datum parameters are invented. There is no
claim of universal EPSG, WKT, WKT2 or Philippine CRS coverage.

Layer records retain `sourceCrs`, `sourceSrsId`, `sourceCrsDefinition`, source file
and table names, `normalizedCrs: EPSG:4326`, and `mapCrs: EPSG:3857`.
Source metadata is not used as a substitute for transforming coordinates.

Point, MultiPoint, LineString, MultiLineString, Polygon and MultiPolygon are
supported. Coordinate order, multipart structure, rings and ordinary holes are
preserved. XYZ heights are retained but not vertically transformed. XYM/XYZM,
curves, geometry collections, generic GEOMETRY tables, required unknown geometry
extensions, and mixtures inconsistent with a concrete table declaration are
unsupported. Null, empty or malformed geometries reject the whole selected batch;
they are never silently dropped. This is structural validation, not a complete
topological repair/validation engine.

Non-finite coordinates, invalid lines, open/short polygon rings, mismatched
geometry/table SRS or dimensions, and positions outside the Web Mercator latitude
range (approximately ±85.05113 degrees) are rejected.

Deterministic controls include WGS84 [121,14], Web Mercator
[13469658.385986103,1574216.548161465] at that same location, and UTM 51N
[500000,0] at longitude 123 / latitude 0. Expected coordinates are fixed independent
values, not generated by the conversion under test. Tests cover multipart, line,
polygon, bounding extents, actual OpenLayers coordinates and browser map fitting.

## GeoJSON compatibility correction

Previously, GeoJSON CRS metadata was detected for display while all coordinates
were still read as EPSG:4326. Explicit supported CRS declarations now transform
their actual coordinates to WGS84 first. EPSG names, OGC EPSG URNs/URLs and CRS84
are recognized; unsupported explicit declarations fail instead of misleading map
placement. Stale declared CRS/bounding metadata is removed after normalization.
Ordinary RFC 7946 GeoJSON retains its existing WGS84 behavior. Other format
parsers were not rewritten.

## Attributes and managed-layer behavior

Text, ordinary numbers, integer boolean-compatible values and nulls are retained.
Integers outside JavaScript's safe range become exact decimal strings; SQLite
date-like text remains unchanged; binary values become reversible `hex:` strings.
Non-finite numeric values fail explicitly. This policy avoids JSON/Share errors
and silent integer rounding. Primary keys remain properties and feature IDs;
reading proceeds in primary-key order. Category and SLD matching rules were not
changed.

Non-geometry attributes named `geometry` or `__proto__` conflict with OpenLayers
property storage and cause an explicit table rejection with field-renaming
guidance. Generated/hidden columns and virtual tables are also unsupported.
Unusual text and table names are rendered using text nodes or existing escaped
markup. The QA fixture intentionally includes HTML-like text to check escaping.

Table-derived friendly layer names receive numeric suffixes on collisions.
Existing layers are not overwritten. GeoPackage layers reuse visibility, order,
opacity, renaming/removal, attributes, label fields and the existing point, line
and polygon styles. Optional existing SLD import uses the same attribute values
and legend controls. No GeoPackage-specific style or output controls were added.

All selected tables are read and converted before registration. Any bad selected
table prevents all additions. Registration failures remove every addition from
the map, store and panel, restoring the previous active selection. Browser tests
inject a failure after a map layer has been added to verify this cleanup.

Shared defects corrected during integration: degenerate point/horizontal/vertical
extents could not be fitted; a fast modal reopen could be closed by a pending
animation; source-derived attribute-dialog headings needed HTML escaping; vector
registration needed cleanup if an operation failed after adding the map layer.

## Validation, resource limits and cleanup

| Limit per selection/import | Value |
| --- | ---: |
| File size before reading | 50 MiB |
| Metadata tables/rows per metadata query | 200 |
| Columns per table | 256 |
| Features across selected tables | 50,000 |
| Coordinate positions across selected features | 1,000,000 |
| Estimated retained attribute data | 32 MiB |
| Individual attribute value | 1 MiB |

Limits are conservative application safeguards, not a guarantee that every file
under them fits every device. Estimated string memory uses two bytes per code
unit; binary values are budgeted after hexadecimal expansion. A generated
5,844,992-byte file containing 50,000 points successfully passed parsing and
OpenLayers conversion; the measured Node read/conversion phase was approximately
0.56 seconds locally. A 50,001-feature table was rejected before extraction.
This establishes a small-feature boundary, not browser heap bounds for 50 MiB
complex polygon datasets.

SQLite work, WKB reading and projection run in a dedicated worker. The File is
passed to that worker and read once; discovery reuses the database for Upload.
Prepared statements are always freed in `finally`, including failed reads.
Database handles close after reading/error, and worker termination releases WASM
memory after success, error, replacement or clear. Chrome target checks verified
that no GeoPackage workers remained after the browser workflow.

Queries use fixed SQL, bound values and quoted identifiers, never uploaded SQL.
Views, virtual tables and required unknown read extensions are rejected.
SQLite is put in query-only mode with trusted schema disabled. The map sees no
features until validation finishes. There are no runtime parsing timeouts used
to conceal blocked processing.

Final OpenLayers feature construction and layer registration remain on the main
thread, as required by the existing architecture. Large valid imports may pause
the UI during that final stage. GeoJSON and OpenLayers feature representations
are both retained because existing attributes/styles/outputs use them. Repeated
huge imports still accumulate managed layers; per-import limits do not impose a
global session memory ceiling.

## Dependency/security review

`npm audit` reported **6 existing findings: 4 high, 1 moderate, 1 low**.
The affected installed versions also appear unchanged in the original HEAD
lockfile: Vite 7.3.2, esbuild 0.27.7, nanoid 3.3.11, postcss 8.5.9,
source-map-js 1.2.1 and fflate 0.8.2. No advisory was reported against the newly
added GeoPackage reader or its new dependency entries at review time.

`npm audit --omit=dev` reports the existing production **fflate** moderate finding,
[malformed ZIP64 denial of service](https://github.com/advisories/GHSA-px8p-9vwx-vf98).
The remaining advisories concern existing build/dev tooling, including Windows
Vite path/editor handling and source-map processing. Follow up with targeted
updates of those existing dependency chains and repeat their regressions. No
unrelated audit fixes or blanket upgrades were applied in this feature.

The primary package, SQLite runtime, wkx and proj4 carry MIT licenses. The browser
bundle also carries third-party notices including Apache/BSD material; Vite emits
those notices and upstream license texts with the distribution. Passing an audit
does not establish that every possible hostile SQLite/WKB file is harmless;
bounded input, read-only operations, strict extraction and worker isolation remain
part of the import design.

## Remaining limitations and tests not performed

- No raster/tile/elevation rendering, editing, `.gpkg` writing or save-back.
- No universal CRS support, inferred PRS92 shift, external datum grids, vertical
  datum transformation, topology repair, measured/curved or generic mixed geometry.
- No Firefox/Safari/mobile verification, remote GitHub Pages deployment, clean
  Linux Actions installation, real production SMTP delivery or production database
  storage verification. Windows Chrome dev/production preview was tested.
- The offline browser tests remove external basemaps to exercise deterministic
  vector output. Existing static-output tests use controlled tile responses;
  live third-party map-server availability was not tested.
- Exact process/heap profiling and exhaustive hostile-database fuzzing were not
  performed. No claim is made about worst-case complex files at the 50 MiB cap.

## Manual acceptance instructions

1. Run `npm run dev`, open **Add Geospatial Data**, select **GeoPackage (.gpkg)**,
   and choose `tests/fixtures/vector-multitable.gpkg`. Confirm filename, size and
   three checked table rows with geometry/count/CRS metadata.
2. Import only `facilities`. Confirm one Facilities layer at longitude 121,
   latitude 14 and a useful map fit. Inspect its attributes; the HTML-like name
   must be literal text, large integer `9007199254740993` exact, null blank,
   binary `hex:00ff0a`, and date text unchanged.
3. Reopen and import all three tables. Confirm Facilities 2, Roads and Land Use
   are separate records, with the original Facilities preserved. Check visibility,
   opacity, order, rename/removal and zoom-to-layer. Check labels and label-field
   selection; verify polygon holes and line/point appearance.
4. Apply existing compatible point/line/polygon SLD files using the fixture's
   `category` field (value `A`). Check rule labels, symbols, legends and manual/SLD
   switching. Exercise categorized polygon styling through the existing controls.
5. Verify Export and Share normal/enlarged previews. Hide one layer and confirm
   its heading disappears. Generate PNG, JPEG and PDF and inspect the entire
   composition, legend order, north arrow and footer. Use an authorized QA
   recipient only if performing a real Share email acceptance test.
6. Prepare equivalent WGS84, EPSG:3857 and UTM 51N datasets in a GIS; verify the
   same geographic placement and bounds. A dataset with undefined CRS or PRS92
   without datum parameters must give reprojection guidance, not misplaced data.
7. Exercise invalid/empty `.gpkg`, corrupt bytes, raster-only, unsupported/empty
   vector tables, null geometries and an oversized file. Selected-table failures
   must leave the current map intact. Clear or replace the file during discovery,
   close/reopen the modal, and recover by selecting a valid file.
8. Import ordinary Shapefile ZIP, WGS84 GeoJSON, explicitly projected GeoJSON,
   KML and latitude/longitude CSV. Repeat core steps with `npm run build` followed
   by `npm run preview`; inspect the browser console/network for local worker/WASM
   loading failures.
